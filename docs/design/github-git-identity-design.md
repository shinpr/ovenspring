# GitHub account for factory Git operations

## Overview

Every commit the factory creates takes the configured GitHub token's account as author and committer. Every factory Git command that talks to `origin` authenticates with that same token. It runs only while `origin` still points at the repository the GitHub connection was built for, so reads and pushes never reach another destination. Authentication never comes from the machine's credential helper, its netrc, an inherited HTTP header or the SSH identity, and the token goes to no other host, proxy or submodule remote. The factory adds these overrides only to its own Git child processes, so the owner's Git configuration and stored credentials keep their values.

## Background and Context

### Prerequisite ADRs

- [ADR-0007](../adr/ADR-0007-daemon-owns-external-writes.md#decision): the daemon holds the GitHub credential and makes every push. This design keeps the token inside the daemon's own Git commands. Agents still run as the owner's user, as that ADR records.
- [ADR-0006](../adr/ADR-0006-agent-launch-permissions-and-guard.md#decision): agent launches and their guard are unchanged.

### External Resources Used

| Resource | Feature-specific identifier | Notes |
|---|---|---|
| GitHub connection (Connect, [GUIDE.md](../GUIDE.md#connect)) | REST `GET /user`, fields `id` and `login` | The existing authenticated viewer request, with the current token and grants |
| GitHub Git over HTTPS | `origin`'s URL when the GitHub connection was built, the URL its `RepoId` is parsed from | Fetch, `ls-remote` and push, with the token as the HTTPS password |

### Requirement Convergence

- **Outcome**: The commits the factory creates and the pushes it sends are attributed to the GitHub account whose token the owner configured, not to whoever is logged in on the machine (`state/sources/issues/GH-34.md`, Outcome).
- **Requirements**: These come from the issue's Requirements and Done when, and from the owner's answers.
  - Both author and committer of every factory-created commit are the token's account. This covers issue commits, local base and branch merges, and the agreements commit.
  - Every factory push authenticates with the configured token. It succeeds when the machine's credential helper holds no GitHub login.
  - The owner's Git configuration and stored credentials keep their values.
  - The commit-identity rule in [Factory Core Design](factory-core-design.md) states the new behavior.
- **Owner's decisions**:
  - Name and email are the `login` and `{id}+{login}@users.noreply.github.com` from authenticated `GET /user`. They use the current grants and add no Connect input. A legacy account may lose its profile link (`GH-34-spec-20.md`, `GH-34-design-21.md`).
  - Where Git would use the machine's SSH identity, the command fails through the existing error path.
  - Credentials are scoped to the factory's Git commands for the connected repository.
  - The design reuses the existing token selection and error handling. It adds no Git error-message parsing, separate login validation or dedicated TLS test server unless removing one would break or leave unverified a GH-34 requirement (`GH-34-design-21.md`).
- **Non-Goals**: Commits already pushed keep their authorship. Commits the owner makes by hand are out of scope. Pushing to norsica and deployment checks, results and fallbacks are excluded (`GH-34-spec-19.md`).
- **Left open by the owner**: None.

#### Assumed Behaviors

- [x] The four variables `GIT_AUTHOR_NAME`, `GIT_AUTHOR_EMAIL`, `GIT_COMMITTER_NAME` and `GIT_COMMITTER_EMAIL` in a child's environment set both roles of `git commit` and of a two-parent `git merge`. They override `user.*` without writing config. Evidence: [git § Git Commits](https://git-scm.com/docs/git#_git_commits). The codebase analysis also probed this in a temporary repository (`decisionMaterials.reuse`, `worktree::git`). Design effect: none. Confirmed: Yes.
- [x] `GIT_CONFIG_COUNT` with `GIT_CONFIG_KEY_<n>`/`GIT_CONFIG_VALUE_<n>` adds command-scoped config that is read after every config file and is never persisted. A child inherits the daemon's own `GIT_CONFIG_*` entries, so setting `GIT_CONFIG_COUNT` to the factory's count alone drops them, while appending after them keeps them. Evidence: [git-config § ENVIRONMENT](https://git-scm.com/docs/git-config#ENVIRONMENT) (Git ≥ 2.31). Probe for I001, run in a temporary directory with Git 2.54.0. There were two bare repositories, A (connected) and B, `origin` pointed at B, and an inherited `GIT_CONFIG_COUNT=1` entry set `url.<A>.insteadOf=<B>`. Plain `git remote get-url --all origin` printed A. With the inherited entry replaced by a factory entry at index 0, `git fetch origin` fetched B's branch. With the factory entry appended at index 1, `get-url` printed A and the fetch got A's branch. An inherited count with a missing `GIT_CONFIG_KEY_<n>` made Git exit 128 ("unable to parse command-line config") before it contacted a remote. Limitation: the launch guard refuses `git push`, so the probe used fetch. Push resolves `origin` through the same remote config, and `get-url --push` lists its URLs. Design effect: the factory's entries are appended, and the guard and the command run in one environment. Confirmed: Yes.
- [x] An empty `credential.helper` value clears the helper list collected so far. URL-scoped helpers such as `gh`'s `credential.https://github.com.helper` are in that list, so a command-scoped reset removes them all. Evidence: [gitcredentials § Configuration Options](https://git-scm.com/docs/gitcredentials#_configuration_options), and Git's `credential.c`, `credential_config_callback`. All URL-matched entries feed one list, in config order. Confirmed: Yes. The integration test in Verification also exercises it with a URL-scoped owner helper.
- [x] An empty `http.<url>.extraHeader` value, scoped to the exact URL the command contacts, clears every inherited extra header for that URL. That includes an owner header scoped to the same endpoint. A generic `http.extraHeader` reset does not: Git's HTTP options use the URL matcher, which skips a later setting less specific than one already applied. A key equal to the contacted URL matches its host, port, path and user exactly. No other key can be more specific, and on equal specificity the command-scoped entry wins because it is read last. Evidence: [git-config `http.<url>.*`](https://git-scm.com/docs/git-config#Documentation/git-config.txt-httpurl), [git `http.c`](https://github.com/git/git/blob/v2.53.0/http.c#L1219-L1233), [`urlmatch.c`](https://github.com/git/git/blob/v2.53.0/urlmatch.c#L517-L583). Probe for I002, run in a temporary directory with Git 2.54.0. A local HTTP server answered 401 and recorded `Authorization`. Repository config held an owner `http.http://127.0.0.1:<port>/origin.git.extraHeader` and an owner `credential.http://127.0.0.1:<port>.helper` that wrote a marker. `git ls-remote` ran with the command-scoped config under Data Contracts. With a generic `http.extraHeader` reset, the server received only the owner's header. With the reset keyed to the contacted URL, it received no header and then `Basic base64(x-access-token:test-token)`. In both runs the owner helper was not called. Limitation: plain HTTP on localhost, not GitHub. Design effect: the header reset is keyed to the connected URL. Confirmed: Yes.
- [x] `git remote get-url --all origin` and `git remote get-url --push --all origin` list the URLs that a fetch and a push of `origin` use, with `insteadOf` and `pushInsteadOf` expanded. Without `pushurl`, `--push` lists the fetch URLs. Evidence: [git-remote `get-url`](https://git-scm.com/docs/git-remote#Documentation/git-remote.txt-get-url), [git-push § REMOTES](https://git-scm.com/docs/git-push#_remotes). Design effect: the connection guard reads the effective destinations from Git itself (I001). Confirmed: Yes.
- [x] A `!`-prefixed helper runs as a shell snippet with the action (`get`, `store`, `erase`) as its argument. A `get` that prints `username=` and `password=` supplies the HTTPS credential. Evidence: [gitcredentials § Custom helpers](https://git-scm.com/docs/gitcredentials#_custom_helpers). Confirmed: Yes.
- [ ] GitHub accepts a token as the HTTPS Git password with the username `x-access-token`. Evidence: [GitHub, using a token on the command line](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens#using-a-personal-access-token-on-the-command-line) documents the token-as-password part. `gh`'s own Git credential helper hands Git the same token. Design effect: if GitHub required the account's login as username, the helper prints `login` from `viewer()` instead. The Selected Design remains valid. Confirmed: No, because GitHub cannot be reached from the offline lane (Risks).
- [x] Authenticated `GET /user` returns `id` and `login` to classic, OAuth, `gh` and fine-grained tokens with no extra permission. Evidence: [GitHub REST, get the authenticated user](https://docs.github.com/en/rest/users/users#get-the-authenticated-user). Confirmed: Yes.

### Problem to Solve

Every factory commit takes the machine's Git identity, and every factory push authenticates with the machine's credential helper. On the owner's machine, the factory's work is therefore recorded as the owner's personal work and carries the owner's personal email address (`GH-34.md`, Current state).

## Acceptance Criteria

- [ ] **AC1**: When the factory creates an issue commit, a local merge of the base or the branch head, or the agreements commit, `git log --format='%an <%ae> | %cn <%ce>'` on that commit shall show `<login> <<id>+<login>@users.noreply.github.com>` in both roles. Commits it did not create keep their metadata.
- [ ] **AC2**: When the factory pushes, or reads `origin` for the work that leads to a push (including the base fetch of the dashboard's Run the product save), the configured token shall be the only credential the command can send: a push and a read send it with their first request and succeed. The owner's credential helper is never called, a netrc login is never used, an inherited `Authorization` header is never sent, and a password in `origin`'s URL is never used. No other host, proxy or submodule remote receives the token.
- [ ] **AC3**: When the factory commits or pushes, the repository's and the owner's Git config files and stored credentials shall keep their bytes.
- [ ] **AC4**: If `origin` uses SSH, or its URL carries a password, or any fetch or push URL of `origin` differs from the URL the GitHub connection was built from (including after `origin` changes while the daemon runs), then the factory's remote Git command (fetch, `ls-remote` or push) shall fail. This includes a URL reached through a rewrite in the config the command inherits, such as an inherited `GIT_CONFIG_*` entry. The command shall fail without running `ssh` or contacting that URL. The failure shall count as an operation failure (Factory Core AC-062), so two passes in a row stop the issue or sprint with `exception`, and it shall never be recorded as `github-unreachable`.
- [ ] **AC5**: When a factory Git command fails while `origin` passes the check in AC4 and its token-authenticated probe also fails, the failure shall follow Factory Core AC-062. If GitHub refuses the token (`viewer` gets an answer with an error status), it shall count as an operation failure and stop after two passes. Otherwise it shall be retried as `github-unreachable` with `via: git`, and it shall clear once that probe answers.

## Design

### Selected Design

The account and the token come from the `GitHub` service the daemon already holds (`Services.github`). Its token is selected in `daemon_cmd::github_api`: the stored token, or else the `gh` token. A credential change already rebuilds services, so the next Git command uses the new account. The dashboard's base fetch, which runs before the daemon may exist, applies the same selection to the credentials file. Both call one shared `github::selected_token`.

1. **Account.** `GitHub::viewer()` returns `Account { login: String, id: u64 }`. `GitHubApi` decodes it from its existing `GET /user` into a private `RawViewer { login, id }`, so `RawUser` and the review- and comment-author fixtures are untouched. `Account::email()` is `format!("{id}+{login}@users.noreply.github.com")`. A failed or undecodable response is the existing `HttpError` and reaches the daemon as `DaemonError::GitHub`. The existing callers read `.login`: Connect in `setup_checks.rs:99` and the API probe in `pulls.rs:332`.
2. **Git connection.** `GitHub::git_remote(&self) -> GitRemote<'_>` returns `GitRemote { url: &str, token: &str }`. `url` is the `origin` URL, as `git remote get-url origin` printed it, that the client's `RepoId` was parsed from when the service was built. `RepoId::from_remote` reads HTTPS and SSH GitHub URLs only, never plain HTTP, so the token never travels unencrypted. `token` is the token the client already sends as Bearer. It does no I/O.
3. **Commit identity.** `worktree::git_as(dir, &Account, args)` runs `git` with the four identity variables. The issue commit (`issues.rs:1115`) and the agreements commit (`sprint.rs:514`) call `self.github()?.viewer()?` only when something is staged. A lookup failure propagates with `?` before the commit runs, so it never becomes a commit refusal. `merge_from_origin(worktree, github, refs)` calls `viewer()` at the first ref it must actually merge, then runs `git merge` with `git_as`. An ancestor skip needs no lookup. A fast-forward creates no commit.
4. **Remote commands.** `worktree::git_remote(dir, &GitRemote, args)` builds the child environment once: the inherited environment without `GIT_CONFIG_PARAMETERS`, plus the command-scoped config and variables listed under Data Contracts, appended after any inherited `GIT_CONFIG_*` entries. Git reads `GIT_CONFIG_PARAMETERS` (set for processes run under `git -c`) after `GIT_CONFIG_*`, so an inherited helper or header there would override the resets (probe with Git 2.54.0); the factory's own remote commands drop it. The child also drops an inherited `GIT_TRACE_REDACT`, so Git's traces keep `Authorization` redacted, and sets `GIT_TERMINAL_PROMPT=0`, since the daemon has no one to answer a prompt. `fetch` and `push` run with `--no-recurse-submodules`, which outranks any config, so no submodule remote is contacted. Both the guard's reads and the command run in that environment. `git_remote` reads the inherited `GIT_CONFIG_*` and `GIT_CONFIG_PARAMETERS` variables from the daemon's environment and passes them to a private `remote_with(dir, &GitRemote, inherited, args)`, which sets the child's `GIT_CONFIG_*` from them, never passes `GIT_CONFIG_PARAMETERS` on, and does the rest. The unit tests call `remote_with` with chosen inherited entries. Every factory command that talks to `origin` uses it, with unchanged arguments: `push`, `ls-remote` (`pulls.rs:204,292`, `stops.rs:175`), and `fetch` (`pulls.rs:459,704,910`, and the base fetch that moves out of `ensure_detached` into `Daemon::checkout_for` and `setup::settle_app`). The reachability probe of item 6 uses it too.
5. **Connection guard.** Before every command, fetch, `ls-remote` or push, `git_remote` reads `git remote get-url --all origin` and `git remote get-url --push --all origin`. Both run in the environment of item 4, so they expand exactly the rewrites the command applies. `get-url` contacts no remote. It runs the command only when every listed URL equals `GitRemote.url` byte for byte, `GitRemote.url` is not one of the SSH forms `RepoId::from_remote` accepts (it starts with neither `ssh://` nor `git@github.com:`), and `GitRemote.url` carries no password (its user part, between `https://` and `@`, contains no `:`). `RepoId::from_remote` accepts `https://user:password@github.com/…`, and Git sends a password from the URL without asking any helper, so the token would not be used. Since every other destination is refused, no command can reach SSH. Otherwise it returns a `GitError` naming the connected URL and the differing one, without running the command, with `refused_locally` set. A failure of the guard's own `get-url` is marked the same way. Every URL the error names has its password replaced by `***`, so the refusal record carries no credential. Two cases are therefore refused before any credential or write leaves the machine. In one, a `pushurl`, an extra URL or a rewrite leads elsewhere. In the other, `origin` was changed to another repository while the daemon runs and the API is still bound to the connected one. The fix in both is to restore `origin`. A daemon restart also works for a deliberate change, since it rebuilds the connection from the new `origin`. The dashboard's base fetch uses the URL its last passed GitHub check recorded as `GitRemote.url`, so a save after `origin` changed is refused the same way.
6. **Failure classification.** `stops::unreachable` never treats a `GitError` with `refused_locally` as unreachable: the refusal the command met decides, wherever it ran. Otherwise it is `github-unreachable` with `via: git` only when `probe_git()` is `OutOfReach`. `probe_git()` runs `git_remote(ls-remote -q --exit-code origin HEAD)`: success is `Answers`; a local refusal, or no GitHub connection, is `Refused`. When the probe fails otherwise, it calls `viewer()`: `Err(e)` with `out_of_reach(e)` `None` (`HttpError::Status` or `Decode`) means GitHub refused the token, `Refused`; success or `Transient` is `OutOfReach`. Every other result goes to the existing counted path of `settle_for`, which records `operation-failed`, stops after `FAILURES_TO_STOP` passes and files `exception`, as Factory Core AC-062 requires for a local Git failure and for a client error the service answered. `poll_pull_requests` clears an open `via: git` occurrence only on `Answers`; `OutOfReach` records another failure, and `Refused` keeps it open without one, since the operations that meet the refusal count it. This reuses `errors::out_of_reach`, the API's existing transient-versus-refused classification, and reads no Git message text. `Daemon::push` sends its own failure here too. When the push fails and its post-failure probe does not answer, it returns the push's `GitError` instead of recording `push-failed` and returning `Ok(None)`, so `settle_for` classifies the failure on the pass it happens. Before, a push that failed after a successful pre-push fetch went uncounted and opened no notice until a later pass's fetch failed. The issue stays in `pushing` and the next pass pushes again, as before. A probe that answers still yields `PushRefused`. The dashboard keeps its `push-failed` sentence for events recorded by earlier versions.

`git`, `git_as` and `git_remote` share one private executor, which takes a prepared `Command` and maps its output to `GitError` as `git` does today. All other Git calls stay on `git`.

### Error Handling

All failures go through existing paths. The design adds no new kind of failure and no message parsing.

| Failure | Detection | Existing recovery |
|---|---|---|
| No GitHub connection | `self.github()` | `DaemonError::Launch("no GitHub connection is configured")`, as for every PR operation |
| `GET /user` fails or does not decode | `viewer()?` before commit or merge | `DaemonError::GitHub`: unreachable when transient, otherwise a stop with `exception`. A commit is not marked refused. |
| No GitHub token when the dashboard saves Run the product | `selected_token` is `None` in `settle_app` | `AppRefused::Failed`, as a failed base fetch is today |
| Hook refuses commit | `git_as` commit fails | `refused("commit")` → `CommitFailed` → quality correction (unchanged) |
| Merge conflict | `git_as` merge fails | `merge --abort`, `Ok(false)` → `merge-base` / sprint stop (unchanged) |
| Push refused while `origin` answers the token-authenticated probe | push fails, probe succeeds | `PushRefused` → quality correction (unchanged) |
| A fetch or push URL of `origin` is not the connected URL, including after `origin` changed, or `origin` uses SSH or carries a password, or the machine's Git is older than 2.46 | The connection guard refuses before the command runs, and its `GitError` is marked `refused_locally`. | `GitError`, counted by `settle_for` as `operation-failed`. Two passes in a row stop the issue or sprint and file `exception` naming both URLs (AC-062). This is never `github-unreachable`. | Push or read fails, the probe fails, and `viewer()` gets an error status: the token is revoked, expired or refused | `probe_git` is `Refused` through the `viewer()` check | Counted as above: stop and `exception` after two passes (AC-062, a client error the service answered). ## Implementation Plan

**Approach**: vertical slice. The riskiest premise is that a push authenticates with the token alone while an owner helper is present. It is proven first, at the real Git boundary, through the issue push route.

1. `Account`, `viewer()`, `GitRemote` and `git_remote()` in integrations, with the URL passed from `repo_id`, with `FakeGitHub` and the existing callers updated. Everything else depends on it.
2. `worktree` executor with `git_as` and `git_remote`, and the HTTP fixture test of the issue push (Early Verification Point). If the token is not what the fixture receives, or the owner helper is called, stop and revisit the remote-access design before rewiring the other callers.
3. Route the remaining commits, merges, reads and the agreements push. Move the base fetch and `gh_token`, and fetch with the token in `settle_app`. The `ensure_detached` tests in `crates/daemon/tests/worktree.rs` fetch before calling it. Replace the agreements author assertion. Remove the superseded identity comments at `sprint.rs:512` and `pulls.rs:280-282`. 4. The factory-core design rule is already updated with this design. Then run the workspace checks.

No migration: no persisted format changes, and existing commits and refs are untouched.

## Security Considerations

- **Authentication and authorization**: the token is the one the owner configured for the API. `GitHub` repository permissions decide what it may push. Inherited helpers and inherited extra headers are dropped, and the credential is filled before the first request, so a refused token fails instead of falling back to the machine's login, its netrc or an owner-configured `Authorization` header. A Git older than 2.46, which cannot fill the credential first, is refused before anything is contacted. Certificate verification stays on whatever the inherited environment or config says. The connection guard refuses an SSH `origin` before Git runs, so the machine's key is never used.
- **Sensitive data**: the token is only in the Git child's environment and in the helper's stdout to Git. It is not in arguments, URLs, config files or `GitError`. Git's own diagnostics do not print passwords, and its traces redact `Authorization` because the child never inherits `GIT_TRACE_REDACT`. The daemon's environment and agent launches do not receive it. Hooks that Git runs during a push inherit the child's environment and so can read the token. This matches ADR-0007, under which processes running as the owner's user can already reach the owner's `gh` and Git credentials.
- **Destination**: a remote command runs only while every fetch and push URL of `origin`, with rewrites expanded under the same environment the command uses, equals the URL the API connection's `RepoId` was parsed from. A mismatched `pushurl`, an extra URL, a rewrite, or an `origin` changed while the daemon runs or since the dashboard's GitHub check therefore receives neither the token nor a read or write request. Fetch and push never recurse into submodules. The helper releases the token only to the connected host, so a proxy never receives it. Redirects are not followed, so the token never reaches another repository on the same host: a renamed or transferred repository fails the command, and the work stops with `exception` until `origin` is the new URL and the daemon restarts. The guard and the command are two Git processes. A change to `origin` made in the milliseconds between them is not caught (Risks).
- **Input validation**: `id` and `login` come from the authenticated GitHub response. They are passed to Git as environment values, never through a shell.

## Design Boundaries

- **Intentional limitations**:
  - GitHub's final merge commit is created by GitHub's API and is outside this rule.
  - Commits by agents or fake agents in tests are not factory-created commits.
  - A legacy account's commits may lack a profile link, which the owner accepted.
- **Existing extension points used**: the `GitHub` trait (`GitHubApi`, `FakeGitHub`), `Services.github` and its replacement, and the `worktree` Git executor.

## Risks and Mitigation

| Risk | Impact | Probability | Mitigation |
|---|---|---|---|
| A change to `origin` lands between the guard's `get-url` and the command | Medium | Very low | The window is two consecutive Git processes in the same tick. The next command is refused, and the change takes an owner edit during a run. |
| GitHub's Git endpoint refuses a token its API accepts (for example, a fine-grained token without Contents access to the repository) | Medium | Low | The failure is classified as `via: git` unreachable and retried, with a visible `github-unreachable` notice whose cause names the failing Git operation, instead of stopping. The token's repository access is the owner's configuration. |
| GitHub rejects `x-access-token` as the username for a personal or `gh` token | High | Low | `gh`'s own helper hands Git the same token for `github.com`. If a real push is refused, the helper prints `viewer().login` as the username instead, and the design is otherwise unchanged. The first factory push after release shows it. Until then the push retries as `github-unreachable` via git, with a visible notice (Error Handling). |
